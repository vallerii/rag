## Логика в 5 пунктах
1. **Google-таблицы** — найденные лиды. Grok заполняет в них анализ по промпту. Lead CRM раз в час импортирует таблицы в свою базу (Neon) и работает с лидами: звонки, письма, PDF, отправка через LetterXpress.
2. **База RAG (Supabase)** — зарегистрированные компании и всё, что с ними связано. Плюс закрытая служебная копия строк таблиц лидов (таблица `prospects`, видит только команда), чтобы при регистрации сразу находить готовый анализ.
3. **При регистрации RAG сам (кодом) ищет готовый анализ:** сначала у других проверок той же компании, потом в копии таблиц лидов. Нашёл — переносит в проверку клиента, отчёт сразу виден, заново ничего не проверяется. Не нашёл — статус «ждёт анализа».
4. **Grok подключён к базе RAG через свой MCP** и видит только проверки со статусом «ждёт анализа». Автоматизация Grok (grok.com/automations) запускается 2 раза в день: анализирует их по тому же промпту и записывает результат в базу. Клиент получает письмо «Analyse fertig». Если автоматизация не видит MCP — сотрудник запускает Grok вручную 1–2 раза в день.
5. **Менеджер отчёт не собирает и не публикует** — только выборочно проверяет работу Grok.

## Что есть в коде сейчас (25.11) — опираться на это, не изобретать заново

- **Промпт анализа для Grok живёт в CRM:** `lib/letters/rag-analysis-prompt.md` (его же показывает настройка шаблона). Копия в проекте claude.ai — `claude/lead-problems-prompt-2026-11.md`.

Области: `maps` (Befund Google-Profil), `website`, `social`, `ai`.

**RAG (`rag`):**
- `checks` (`supabase/schema.sql`) — одна проверка = одна компания одного пользователя: `place_id`, `place`, `sources`, `audit`, `report_draft`, `report`, `status` (`submitted / in_review / ready`), `source_page` (`crm-<код>` для QR из CRM). Каналы отчёта: `ai`, `maps`, `search` (сайт и поиск), `social` — соответствуют областям CRM `ai`, `maps`, `website`, `social`. Формат отчёта v2 — `claude/check-report-v2-2026-10.md`; архив версий `check_reports` (`supabase/admin.sql`).

- `prospects` (`supabase/prospects.sql`) — закрытая таблица лидов (RLS: только `is_staff()`), импорт сейчас из **опубликованного CSV** (Edge Function `prospects`). Триггер `prospect_prefill`: новая проверка по тому же `place_id` берёт готовый `audit`/`report_draft` из `prospects` или из другой проверки **не старше 30 дней**. Триггер `prospect_responded` отмечает лида «откликнулся».
- Автопроверка `audit-collect` (Places, сайт, PageSpeed). Письма клиентам — Edge Function `notify` (**Brevo**, не Resend).
- Тесты базы: `npm run test:db` (`supabase/tests/db.test.mjs`).

## Решения по итогам разбора кода (25.11)
1. **Сервисный аккаунт — тот же, что у CRM** (только чтение). В Supabase добавить секрет `GOOGLE_SERVICE_ACCOUNT_JSON` с тем же JSON. Таблицы уже расшарены на этот аккаунт — ничего не менять.
2. **Какая таблица (вариант 2):** CRM добавляет в QR `t=<sheet_gid>` кампании: `/check?place=<place_id>&ref=<код>&t=<gid>`. Короткий параметр, QR остаётся читаемым. В RAG список таблиц хранит пары `spreadsheet_id + gid`, по `t` сразу берётся нужная. Если `t` нет (старые письма) — поиск по `place_id` во всей копии.
3. **Строки лидов копируются в `prospects`, а не читаются из Google при каждой регистрации.** RAG раз в час (`pg_cron` → Edge Function) забирает все подключённые таблицы через сервисный аккаунт — как CRM. Регистрация не зависит от скорости и лимитов Google Sheets, а дубли ищет уже существующий триггер `prospect_prefill`. Клиенты эту таблицу не видят.
4. **Заморозка после письма — правилом промпта, а не колонкой.** CRM писать в таблицу не может. Поэтому в промпте Grok: заполненные строки **не перепроверять**; перепроверять только строки, где команда вписала в колонку «Neu prüfen» `ja` (и не ставить её строкам, по которым уже ушло письмо — в CRM это видно в «Last action»). Так данные на сайте совпадают с письмом.
5. **Срок годности анализа — 90 дней** (сейчас в `prospect_prefill` 30). Старше — показываем сразу, но ставим «ждёт обновления».
6. **Письма клиенту — через существующий `notify` (Brevo).**

## Что происходит при регистрации (код RAG, автоматически)
1. Проверка создаётся как сейчас (`createCheck`), с `place_id`, а при QR — с `source_page = crm-<код>` и `t`.
2. **Поиск готового анализа (расширить `prospect_prefill`), по порядку:**
   1. Другая проверка того же `place_id` с готовым анализом не старше 90 дней → взять.
   2. Строка в `prospects` той же таблицы (`t`) с тем же `place_id`; без `t` — любая строка с тем же `place_id`; запасной вариант — по домену сайта → взять.
   3. Ничего → `analysis_status = 'pending'`.
3. **Перенос строки лида в отчёт:** колонки «Befund …», «Platz …», «KI-Antworten» и новые колонки → формат отчёта RAG (каналы `maps / search / social / ai`), оценки той же формулой, что в CRM. Отметить источник (`analysis_source = 'sheet'`, таблица, дата проверки). Отчёт публикуется сразу: `report` + `status = 'ready'` системой, без менеджера. Belege клиенту не показывать.
4. Дальше главная копия — проверка клиента; изменения в таблице на её отчёт не влияют.

## Статусы анализа (новые поля в `checks`)
`analysis_status`: `pending` (ждёт) → `in_progress` (Grok взял; защита от двойного анализа) → `done`. Плюс `analysis_source` (`sheet` / `check` / `grok`), `analysis_at`, `analysis` (сырые поля анализа, jsonb), `analysis_taken_at`.
- `in_progress` дольше 2 часов → обратно в `pending`.
- `done` → `pending` только по правилу «старше 90 дней» или по кнопке «Neu prüfen» (позже).
- Клиент эти поля менять не может (как `guard_staff_fields`).

## Поток 1. Пришёл по QR из письма
1. Grok заполнил строку в таблице, CRM импортировала её и отправила письмо (QR: `place`, `ref`, `t`).
2. Человек сканирует QR → `/check` сразу показывает компанию → **упрощённая регистрация** (только e-mail + пароль или Google).
3. RAG находит анализ (см. выше) и публикует отчёт.
4. Экран загрузки ~1 минута с честным текстом «Wir laden Ihre Analyse vom <дата>» — не изображать проверку «сейчас». В это время реально работает `audit-collect` (свежие данные Google).
5. Отчёт: **без входа** — то же, что в письме (итог и оценки); **после регистрации** — подробная версия (все находки, каталоги, конкуренты, ответы ИИ, рекомендации со ссылками на услуги).
6. Источник заявки — `crm-<код>` (уже работает).

## Поток 2. Пришёл сам (реклама, поиск, сарафан)
1. Находит компанию через «Unternehmen finden» (Places) и регистрируется.
2. RAG ищет готовый анализ (проверки → `prospects` по `place_id`). Нашёл — как в потоке 1.
3. Не нашёл — клиент **сразу** видит часть отчёта из `audit-collect` (Google-карточка, места в Maps, конкуренты, сайт, PageSpeed), `analysis_status = 'pending'`.
4. Текст клиенту: «Ihre vollständige Analyse ist in Arbeit. Sie erhalten sie innerhalb von 24 Stunden per E-Mail.» (Grok, MCP и базу не упоминать.)
5. Grok (автоматизация 2 раза в день) берёт проверку, анализирует, сохраняет → отчёт объединяет данные `audit-collect` и Grok → `done` → письмо «Ihre vollständige Analyse ist fertig» через `notify`.

## Что берём из Places API, а что из Grok
- **Places / `audit-collect`:** рейтинг, отзывы, часы, фото, категории, телефон, сайт, конкуренты, место в Maps, проверка сайта, PageSpeed.
- **Grok:** каталоги, соцсети, ИИ-поиск, детали сайта, которых нет в автопроверке, рекомендации.
- Для лидов Google-данные пишет в таблицу Grok (письмо уходит до регистрации); после регистрации `audit-collect` их освежает.

## MCP для Grok (по документации 25.11)
- **Подключение:** grok.com/connectors → New Connector → Custom → URL → вход, если требуется. Сервер должен быть доступен из интернета. Какой вход Grok принимает (OAuth или токен) — проверить тестом.
- **Сервер:** Supabase Edge Function `grok-mcp` (гайд Supabase «Deploy MCP servers»; официальный MCP SDK или mcp-lite). Vercel не нужен. Адрес `https://<project-ref>.supabase.co/functions/v1/grok-mcp`.
- **Не использовать официальный Supabase MCP** — полный доступ к проекту.
- **Инструменты — ровно два:**
  - `list_pending_analyses(limit)` → проверки с `pending` (переводит в `in_progress`): id, Firma, Branche, Stadt, Adresse, Website, place_id, соцсети, Suchbegriff. Без e-mail, имени и телефона клиента.
  - `save_analysis(id, поля)` → проверка формата (те же колонки, что в таблице), запись, `done`. Только для `in_progress`.
- **Защита:** 1) OAuth через OAuth-сервер Supabase Auth под отдельным служебным пользователем; 2) токен в заголовке `Authorization`, если Grok примет; 3) запасной — длинный секрет в URL, менять раз в месяц. Лог всех вызовов.
- **Автоматизация:** grok.com/automations, 2 раза в день: «вызови list_pending_analyses → проверь каждую компанию по промпту → save_analysis». Если новых нет — ничего не делает.
- **Тест (~30 мин) до разработки:** MCP с одним инструментом `ping` → подключить в Grok → проверить: видит ли Grok инструмент и какой вход предлагает; видит ли MCP автоматизация; минимальный интервал автоматизации; сколько компаний проходит за запуск.
