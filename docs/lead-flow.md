## Логика в 6 пунктах
1. **Лиды живут только в Google-таблицах.** Сторонний ИИ находит компании и записывает их в таблицу. Grok один раз проверяет каждую строку по промпту и дописывает анализ в ту же строку.
2. **Lead CRM** подключает таблицу, команда звонит и отправляет письмо с коротким анализом и QR (LetterXpress). CRM используется не только для RAG — **связи CRM → RAG нет**, CRM ничего в RAG не передаёт.
3. **В базе RAG — только зарегистрированные компании.** Копии всех лидов в RAG нет.
4. **При регистрации RAG сам находит анализ этой одной компании:** сначала у других проверок в своей базе, потом в подключённых таблицах (читает их в этот момент, только чтение). Нашёл — копирует строку в проверку клиента и сразу показывает отчёт. Дальше всё читается из базы RAG, таблица больше не нужна.
5. **Не нашёл — Places + Grok.** Places-автопроверка сразу даёт часть отчёта. Остальное (каталоги, соцсети, ИИ-поиск, место в Google-поиске, рекомендации) доделывает Grok, клиенту приходит письмо «анализ готов».
6. **Перепроверок нет.** Строку в таблице Grok анализирует один раз. Менеджер отчёт не собирает и не публикует, только выборочно смотрит работу Grok.

## Принятые решения (25.11, вечер)
1. **Нет связи CRM → RAG.** RAG сам ищет строку в таблицах только для того, кто зарегистрировался.
2. **Нет копии лидов в RAG.** Таблица `prospects`, импорт из опубликованного CSV, кнопка «Kurzanalyse» в админке, коды писем `?c=` и функция `prospect_place` удаляются (писем из RAG не отправляли, старых QR нет).
3. **Нет перепроверок.** Правило промпта «если колонки заполнены — проверь заново» заменяется на «заполненные строки пропускать». Колонка «Neu prüfen» не нужна.
4. **Кто первый, тот и прав — конфликтов Places и Grok нет:**
   - анализ есть в таблице → Places-автопроверку **не запускаем**, отчёт = анализ из таблицы (совпадает с письмом);
   - анализа нет → сначала Places, потом Grok делает **только то, чего у Places нет**. В инструменте сохранения для Grok просто нет полей, которые принадлежат Places, — перезаписать их нельзя.
   - Если Places не смог (нет Google-карточки, сайт не открылся) — эти пункты отдаются Grok.
5. **Таблицы подключаются в админке RAG:** вставить ссылку на вкладку один раз. RAG читает их тем же сервисным аккаунтом, что и CRM (только чтение). Таблицы уже расшарены на этот аккаунт.
6. **Одна компания — одна строка во всех таблицах.** Если при поиске компания нашлась в двух местах, RAG берёт одну строку (с более свежей датой проверки) и показывает в админке пометку «Dublette: таблица A строка 5 и таблица B строка 9», чтобы команда удалила лишнее.
7. **Параметра `t` в QR нет** — он не нужен, раз компания одна.
8. **Письма о готовом отчёте нет, если отчёт показан сразу.** Письмо «анализ готов» уходит только когда анализ готов позже (Grok или ручной план B).
9. **Тексты на сайте про «отчёт проверяет человек» и «готов за 1 рабочий день» исправляем** (список ниже).
10. **Формулировки ИИ-поиска в письме пока не меняем** — вопрос записан в «Требует проверки».

## Кто за что отвечает
| Часть | Что делает | Чего не делает |
|---|---|---|
| **ИИ поиска лидов** | Находит компании, пишет строку в таблицу (с колонкой Google Maps URL) | Не анализирует |

| **Lead CRM** | Импорт таблиц, звонки, письмо с QR | Не пишет в таблицы, ничего не передаёт в RAG |
| **RAG — сайт** | Регистрация, кабинет, отчёт | Клиент таблицу не видит |
| **RAG — база** | Только зарегистрированные компании и их анализ (скопированная строка, данные Places, данные Grok) | Не хранит лидов, которые не зарегистрировались |

## Как найти строку компании (ключ компании)
В таблице «Köln 134» колонки Place ID нет. Что есть (из 79 строк с анализом): ссылка Google Maps с номером карточки `cid` — 33, сайт — 51, телефон — 68; без `cid` и без сайта — 24.

Поиск строки по порядку, первое совпадение:
1. **`cid` карточки Google** — из колонки «Google Maps URL» (`…/maps?cid=7250517857609394766`). У компании на сайте тот же `cid` есть в ответе Places (`googleMapsUri`). Самый надёжный ключ.
2. **Домен сайта** (без `www.`, без пути).
3. **Телефон** (только цифры, `+49` и `0` в начале приравниваются).
4. **Название + индекс** (обе нормализованы; только точное совпадение).

Ссылки вида `maps/search/?api=1&query=…` ключом не считаются — это просто поиск. Нет совпадения — строки нет, анализ делает Places + Grok.

## Подключение таблиц (админка RAG)

## Поток 1. Пришёл по QR из письма
1. Grok заполнил строку, CRM отправила письмо. QR сейчас: `/check?place=<place_id>&ref=<код>`, без place_id — `/check?q=<название город>&ref=<код>`. В таблицах place_id нет, поэтому **CRM добавляет в QR `cid`**, если он есть в ссылке Google Maps: `/check?cid=<cid>&ref=<код>` (одна правка в `ragLink`, `lib/letters/rag.js`).
2. Человек сканирует QR → RAG по `cid` находит строку и показывает только название компании и город → **короткая регистрация: e-mail + пароль** (или Google). Без шагов «проверьте сайт и соцсети».
3. RAG копирует строку в проверку, считает оценки той же формулой, что CRM, публикует отчёт системой. Экран загрузки с честным текстом «загружаем вашу проверку от <дата>».
4. Человек сразу в кабинете с полным отчётом (все находки, конкуренты, ответы ИИ, рекомендации), «Stand: <дата проверки>», без колонки Belege. Письма «отчёт готов» нет.
5. Places-автопроверка не запускается. Источник заявки — `crm-<код>` (уже работает).
6. Без `cid` в QR (у компании нет Google-карточки) — как сейчас: поиск по названию, затем поиск строки по домену / телефону / названию + индексу.

## Поток 2. Пришёл сам
1. Регистрация как сейчас (поиск компании через Places, шаги проверки).
2. RAG ищет анализ: другая проверка той же компании → строка в таблицах (по ключу выше). Нашёл — как поток 1, п. 3–5.
3. Не нашёл → Places-автопроверка (`audit-collect`) сразу даёт часть отчёта: карточка, отзывы, место в Maps, конкуренты, сайт, PageSpeed. Статус анализа «ждёт».
4. Текст клиенту: анализ в работе, полный — в течение 24 часов на e-mail.
5. Grok (план B вручную, позже MCP) делает остальное → отчёт = Places + Grok → письмо «анализ готов».

## Статусы (новые поля в `checks`)
- `analysis_status`: `none` (анализ не нужен, например «с нуля») / `pending` (ждёт Grok) / `in_progress` (Grok взял; дольше 2 часов → обратно `pending`) / `done`.
- `analysis_source`: `check` (взят у другой проверки) / `sheet` (из таблицы) / `grok` / `manual` (план B).
- `analysis` (jsonb): скопированная строка таблицы целиком + откуда (таблица, вкладка, номер строки, дата проверки) или ответ Grok.
- `analysis_at`, `analysis_taken_at`, `reviewed_at` / `reviewed_by` (выборочная проверка менеджером, ничего не блокирует).
- `status` остаётся тем, что видит клиент: `submitted` → `ready`. `in_review` («проверяет менеджер») для новых проверок не используется.
- Клиент эти поля менять не может (защита как `guard_staff_fields`; новая версия функции — в новом SQL-файле, запускать после `project.sql`).
- Срок годности анализа не проверяем (перепроверок нет): показываем любой с датой.

## Grok через MCP — последний этап
Доступа к Grok пока нет, поэтому делаем в самом конце. До этого анализ «ждущих» делается по плану B.
- **План B (раньше MCP):** в админке кнопка «Задание для ИИ» — промпт + список ждущих компаний без личных данных и без пунктов Places → скопировать в Grok (или любой ИИ) → ответ JSON вставить в «Результат» → RAG проверяет формат и сохраняет → письмо «анализ готов».
- **MCP:** Supabase Edge Function `grok-mcp`, два инструмента: `list_pending_analyses` (только `pending`, переводит в `in_progress`; без e-mail, имени и телефона клиента; с тем, что уже знает Places) и `save_analysis` (только поля Grok, только для `in_progress`). Не использовать официальный Supabase MCP. Защита — ключ (сначала проверить тестом с одним инструментом `ping`, какой вход Grok принимает). Автоматизация Grok 2 раза в день.
